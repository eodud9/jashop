# 06. 기술·제품 의사결정 기록(ADR) 및 미결 사항

**목적:** 기술을 단순히 나열하지 않고 **왜 선택했는지·무엇을 포기했는지·언제 재검토할지** 기록한다. 면접에서 구현 이유와 한계를 설명할 때도 사용한다.

## 1. 상태 정의와 문서 우선순위

- **[확정]**: 사용자 경험/대화를 통해 결정된 비즈니스 요구. 구현하면서 임의 변경하지 않는다.
- **[권장]**: 구현·데이터 정합성을 위해 제안한 기술 선택. 실제 코드 작성 중 변경 가능하나 근거와 검증을 남긴다.
- **[미결]**: 최종 제품 정책이 결정되지 않음. 편의로 확정처럼 구현하지 않는다.

**판단 우선순위:** 사용자가 직접 확정한 최신 운영 정책 → 해당 정책을 기술적으로 보존할 수 있는 일관된 구현 → 기존 문서의 기계적 요약/제안. 실제 구현의 변경은 README, 요구사항, ERD, API, 테스트에 함께 반영한다.

## 3. 구현 전략과 대안

### A-01. 같은 재고 요청의 수락 경쟁 — 조건부 UPDATE [권장]

- **문제:** 두 직원이 거의 동시에 REQUESTED를 읽고 둘 다 수락 처리할 수 있음.
- **선택:** `UPDATE ... WHERE status='REQUESTED' AND assigned_to IS NULL`; DB 영향 행 수가 1일 때만 성공.
- **대안:** `SELECT ... FOR UPDATE` 후 상태 검사, 또는 낙관적 잠금 `@Version`.
- **이유:** 단일 행의 단순 상태 전이에 조건부 UPDATE가 짧고 명시적. InnoDB의 행 잠금과 SQL 원자성을 활용.
- **한계:** 직원의 **현재 근무 자격**과의 경쟁은 별도로 직원 잠금/트랜잭션으로 해결해야 함. SQL 하나만으로 모든 업무 정책을 자동 보장하지 않음.
- **검증:** 20개 동시 요청에서 정확히 한 명의 업데이트 행 수 1, 나머지는 0/충돌.

### A-02. 다른 지원 요청 간 직원 중복 배정 — User 잠금 [권장]

- **문제:** `(support_request_id,user_id)` UNIQUE만으로 다른 SupportRequest의 같은 직원 배정을 막지 못함.
- **선택:** 요청 행을 잠가 정원을 확인하고 대상 User를 ID 오름차순 잠근 후 활성 배정 검사.
- **대안:** 활성 배정 전용 유일 키/부분 유일성에 상응하는 생성 컬럼, 전용 현재 배정 테이블, 분산 락.
- **이유:** MySQL 단일 인스턴스에서 명확한 트랜잭션 일관성을 얻음. 불필요한 Redis 분산 락 회피.
- **한계:** 잠금 대기/데드락 위험, 체크아웃·지원 이동 로직도 같은 규칙 필요.
- **검증:** 두 요청의 같은 직원 동시 배정, 정원 1명에 서로 다른 직원 동시 배정, 체크아웃 경합.

### A-03. 마지막 확인값과 확인 이력 분리 [확정/권장]

- **문제:** 최신값만 저장하면 언제 누가 확인했는지 추적할 수 없음. 이력만 조회하면 최신값 조회 때 비용 증가.
- **선택:** StockVerification은 append-only 이력, StockRecord는 `(variant,location)`당 최신 스냅샷 한 행.
- **대안:** 최신 이력을 매번 `ORDER BY verified_at DESC LIMIT 1`로 조회.
- **이유:** 화면 응답과 감사 이력의 역할을 분리.
- **한계:** 두 테이블 간 원자적 갱신 필요; 완료 순서와 실제 관찰 시각이 다를 수 있음.
- **검증:** INSERT/UPDATE 중 한 단계 실패 시 전체 롤백, 0/NULL 구분, 동시 최초 생성.

### A-04. 재고 확인 완료 — 단일 MySQL 트랜잭션 [권장]

- **선택:** Request 상태, Verification 이력, StockRecord 최신값, Notification/Delivery 생성까지 단일 DB 트랜잭션.
- **대안:** 확인값을 먼저 저장한 뒤 나머지를 비동기 이벤트로 처리.
- **이유:** 핵심 업무의 이력·마지막 확인값 간 불일치를 방지.
- **한계:** 알림 DB 저장 실패로 핵심 업무도 롤백될 수 있음. 외부 푸시 전송은 트랜잭션 밖으로 분리.
- **재검토:** 메시징/외부 시스템 통합이 늘면 Transactional Outbox 고려.

### A-05. 알림 전송 — DB 기반 Delivery Worker [권장]

- **선택:** Notification/Delivery를 MySQL에 기록, 별도 Worker가 짧은 선점 트랜잭션 → 외부 전송 → 상태 갱신.
- **대안:** 요청 중 즉시 외부 푸시 호출, Kafka, 외부 작업 큐.
- **이유:** 소규모 MVP에서 운영 복잡도를 줄이면서 장애 복구와 재시도 학습 가능.
- **한계:** 처리량이 증가하면 DB 폴링 비용/지연 발생, 외부 응답 불명확 시 중복 푸시 가능.
- **재검토:** 지연·비용·부하 측정 후 Kafka/전용 큐/Outbox 고려.

### A-06. 실시간 이벤트 — SSE + REST + Web Push [권장]

- **선택:** 사용자가 화면을 보고 있을 땐 SSE로 알림·업무 변경 힌트, 화면은 REST로 최신 상태 재조회. 백그라운드에서는 Web Push.
- **대안:** WebSocket, 일정 간격 폴링만 사용.
- **이유:** 메시지 대부분이 서버→클라이언트 단방향, CRUD는 REST가 담당.
- **한계:** SSE 재연결·인증·멀티 인스턴스 브로드캐스트 필요, 푸시 도달 보장은 없음.
- **재검토:** 양방향 실시간 협업·채팅 등 요구 시 WebSocket 검토.

### A-07. Redis 범위 제한 [권장]

- **선택:** 최근 조회 LIST만 Redis에 저장, 업무 상태는 MySQL.
- **대안:** 전체 상품/수량/업무 요청을 Redis 캐싱.
- **이유:** 캐시 불일치와 장애 범위를 줄임. Redis가 없어도 핵심 업무 정상 처리.
- **한계:** 최근 조회 UI는 일시적으로 비어 보일 수 있음.

### A-08. 인증 — JWT + AuthSession [권장]

- **선택:** Access Token은 검증 가능한 JWT, Refresh는 MySQL 세션/해시/회전/폐기.
- **대안:** Redis Refresh 저장, 서버 세션 방식, 외부 인증 제공자.
- **이유:** 이미 학습한 Spring Security/JWT와 관계 DB 트랜잭션을 연결해 세션 수명 주기를 명확히 구현.
- **한계:** JWT는 발급 후 자동 폐기되지 않으므로 계정 상태·권한 변경의 반영 정책이 필요. Refresh 쿠키는 CSRF 보호가 필요.

### A-09. Flyway + JPA validate [권장]

- **선택:** 스키마 변경은 SQL 마이그레이션으로 남기고 JPA는 생성/수정하지 않고 검증.
- **대안:** 개발 편의를 위한 `ddl-auto=update`.
- **이유:** 인덱스·UNIQUE·CHECK·생성 컬럼 같은 MySQL 중심 제약을 명시적으로 관리.
- **한계:** 초기 마이그레이션 작성 비용 증가. 코드와 DDL이 어긋나면 빌드/기동 실패.

### A-10. 모노레포 [확정]

- **선택:** 루트 하나의 Git 저장소에 `jashop-backend/`, `jashop-frontend/`, `docs/`, `README.md`.
- **대안:** 백엔드·프론트엔드 별도 저장소.
- **이유:** 개인 프로젝트에서 API·문서·두 앱을 함께 변경·리뷰하기 편리.
- **한계:** 프로젝트 규모가 커지면 CI 경로별 빌드 전략 필요.

## 4. 기존 문서·대화 간 불일치 정리

| 항목 | 기존 요약 문서의 변경/혼선 | 이번 상세본의 기준 | 이유 |
|---|---|---|---|
| 가입 식별자 | `loginId`가 추가되거나 가입자가 `storeId` 입력 | **email + password + name**, 가입 후 총괄이 역할/기본 소속 지정 | 초기 확정 요구사항에 충실; 가입자 자기 소속/권한 확정 금지 |
| 승인 API | `/users/{id}/approve`로 변경 | `/admin/users/{id}/approve` | 승인 전용 관리자 영역을 명시 |
| 퇴근 안내 경로 | `/check-out-notices`와 `/checkout-notices` 혼용 | **`/checkout-notices`** | 초기 확정 API 경로 유지 |
| 체크아웃 | `attendanceId` 요청 본문을 필수화 | **`POST /attendances/me/check-out`, 본문 없음** | 초기 대화에서 현재 활성 출근을 서버가 찾는 방식으로 합의 |
| 최근 상품 조회 | `/users/me/recent-products`가 등장 | **`/products/recent`** | 원래 합의한 엔드포인트 유지; 식별자 단위는 variant |
| WorkSchedule.endAt | 필수/제거로 흔들림 | **nullable** | 경기일 미정 + 비경기일 예정 종료 둘 다 필요 |
| 출퇴근 시간 | 원본과 운영 기록 혼용 위험 | **checkOutAt / recordedCheckOutAt 분리** | 실제 시각 불변, 부매니저 30분 단위 직접 지정 |
| 지원 요청의 방향 | `requestingStoreId`, `targetStoreId` 의미 혼동 가능 | 요청한 매장=받는 곳, targetStore=보내는 곳 | 승인/배정은 보내는 매장 부매니저 수행 |
| 승인자 | 모든 MANAGER 동작으로 서술할 위험 | 기본 근무 매장 AM이 출퇴근 승인 | 예외 승인 권한은 별도 정책 미확정 |
| README 경로 | `backend/`, `frontend/`가 아직 없다고 기술 | 실제 `jashop-backend/`, `jashop-frontend/` | 이미 프로젝트 생성 완료 |
| 기술 버전 | 문서에서 버전 개략화 | 사용자가 만든 `Spring Boot 4.1.2` / `Java 21` 기준 | 실제 Gradle 정보 반영 |

문서에 추가한 `eventKey`, Delivery Worker claimToken, `active_work_date` 생성 컬럼, attendance_id 지원 배정 스냅샷 등은 **업무 규칙이 아니라 구현 제안**이다. 확정 데이터 모델 17개를 유지하면서 해당 테이블 안에만 확장 후보로 제시했다.

## 6. 앞으로 ADR 작성하는 방법

각 중요 변경 시 `D-YYYYMMDD-NN` 형태로 아래 항목을 추가한다.

```markdown
### D-202611xx-01: <결정 제목>
- 상태: 제안 / 채택 / 폐기
- 배경: 어떤 실제 문제가 있었는가?
- 고려한 대안: A, B, C
- 선택: 무엇을 선택했고 왜인가?
- 한계/위험: 무엇이 남는가?
- 검증: 테스트·부하 측정·오류 재현 결과
- 관련 문서/PR: 링크
```

코드가 동작하는 사실만으로 설계가 옳다는 결론을 내리지 않는다. **기술 선택 이유와 실패했을 때의 영향 범위**를 설명할 수 있게 기록한다.

## 7. 구현 결정 기록

### D-20261107-01: Store만 첫 Flyway 마이그레이션으로 도입

- 상태: 채택.
- 배경: 기존 DB 데이터를 보존하면서 첫 영속성 기능을 검증해야 했다.
- 점검: 이름 변경 전 로컬 MySQL 8.4.11의 스키마는 테이블/이력 0개, utf8mb4_0900_ai_ci였다.
- 선택: V1은 stores만 생성한다. 자동 baseline은 끄고 clean을 금지하며 적용 SQL을 검증한다.
  적용 직전 빈 스키마를 재확인한 후 V1을 적용했다. JPA는 validate만 수행한다.
- 대안: 전체 17개 테이블 일괄 생성, Hibernate update, 자동 baseline. 현재 범위와 데이터 보호 원칙에 맞지 않아 제외했다.
- 검증: 일회성 MySQL에서 V1 최초 적용, 커밋된 행을 보존하는 재실행 no-op,
  이력 없는 비어 있지 않은 스키마 거부, 체크섬 변경 감지. 로컬 비웹 기동 2회도 성공했다.
- 한계: 기존 로컬 DB는 비어 있었다. 데이터가 있는 다른 DB의 도입은 별도 점검이 필요하다.
  User/Store API, 권한 검증, 나머지 테이블은 구현하지 않았다. 적용된 V1은 수정하지 않는다.
- 관련: [ERD](03-erd.md), [아키텍처](05-architecture.md), [개발 계획](07-development-plan.md).

### D-20261107-02: UTC 시각과 별도 MySQL 통합 테스트

- 상태: 채택.
- 선택: Store는 호출자가 Clock으로 만든 Instant를 받아 생성/변경 시각을 기록한다.
  JDBC 시간대 UTC와 TIMESTAMP 매핑을 명시해 MySQL DATETIME(6)에 저장한다.
  JPA 자동 감사나 DB 자동 시각 갱신 대신 변경 메서드에서 시각을 함께 설정한다.
- 이유: 기존 Clock을 활용하고 테스트에서 시간·마이크로초를 고정할 수 있다.
  도메인에 시스템 시계나 Spring 의존성을 추가하지 않는다.
- 테스트: Boot BOM의 Testcontainers 2.0.5와 ServiceConnection으로 기존 Compose DB와 분리한다.
  테스트 의존성만 추가하며 H2로 MySQL 동작을 대체하거나 Docker 부재를 스킵하지 않는다.
- 검증: 전체 29건 통과(공통 20 + MySQL 9). UTC 원시 DATETIME 값, dirty checking,
  코드 UNIQUE, 비활성화 시 행/생성시각 보존을 확인했다.
- 한계: 이름 변경/비활성화 명령의 인가는 후속 서비스/API 단계에서 구현한다.
  이력/동시성 제어는 각 업무 기능에서 추가하며, Store 테스트로 증명했다고 주장하지 않는다.
- 관련: [아키텍처](05-architecture.md), [개발 계획](07-development-plan.md).


### D-20261109-01: 프로젝트 이름을 jashop으로 통일

- 상태: 채택.
- 배경: GitHub 저장소 이름 변경에 맞춰 로컬 프로젝트 이름을 정리한다.
- 선택: 루트·백엔드·프론트엔드 폴더, Java 패키지·애플리케이션 클래스, Gradle/npm 이름, 문서와 로컬 설정을 함께 변경한다.
- 이유: 패키지 경로와 클래스 이름을 함께 바꿔 컴파일·자동 컴포넌트 탐색의 일관성을 유지한다.
- 한계: 기존 MySQL 스키마·계정·컨테이너·볼륨은 자동 이전하지 않는다. Compose의 기본 프로젝트명·볼륨명은 루트 폴더명에 따라 바뀌므로 기존 데이터 사용 시 연결 대상을 별도로 맞춰야 한다. 적용된 Flyway SQL은 변경하지 않는다. 과거 로컬 DB 검증 기록은 이름 변경 이전의 결과다.
- 검증: 이름 변경 후 백엔드 전체 테스트 29건 통과, 프론트엔드 `npm run build`·`npm run lint` 통과. 기존 추적 파일 67개 보존 및 Flyway 마이그레이션 원문 일치를 확인했다.

### D-20261109-02: User 영속성과 V2 users 도입

- 상태: 채택.
- 선택: UserRole/UserStatus를 VARCHAR 문자열로 저장하고 가입 대기 생성은 STAFF/PENDING/소속 없음으로 제한한다. 매장·승인자는 ID만 참조하며 DB FK로 존재를 보호한다.
- 이유: 기존 package-by-feature 및 Store의 Clock/UTC DATETIME(6) 방식을 유지하고, 불필요한 양방향 연관관계와 enum 순서 의존성을 피한다. 이메일은 strip + Locale.ROOT 소문자 정규화를 공통 함수로 제공한다.
- DB 보호: 이메일 UNIQUE, 역할/상태 CHECK, ACTIVE 직원·부매니저 소속 필수 CHECK, 매장·승인자 FK와 삭제 제한. V1은 수정하지 않고 V2를 추가했다.
- 한계: 비밀번호 해시는 호출 서비스가 생성한다. 이메일 형식·비밀번호 입력 기준, 승인자 자격/담당 매장 인가, 승인·거절·비활성화 상태 전이와 초기 MANAGER 생성은 후속 작업이다. Repository/엔티티를 HTTP 응답으로 직접 노출하지 않는다. 기존 로컬 DB·볼륨은 변경하지 않는다.
- 검증: `./gradlew test --offline` 전체 43건 통과(실패/스킵 0). User 14건 추가, 기존 29건 회귀 통과. CHECK 예외 타입 기대값 오류 4건은 수정 후 해결했다. V1 원문 보존을 확인했다.

### D-20261109-03: 공개 회원가입 API와 비밀번호 해시

- 상태: 채택.
- 선택: auth 기능에 DTO/Service/Controller를 추가한다. 입력은 이름·이메일·비밀번호로 제한하며 미허용 필드는 400으로 거부한다. STAFF/PENDING/소속 없음은 서버가 지정한다. 이메일은 형식 검증 전에 정규화한다.
- 비밀번호: 기존 Spring Security의 DelegatingPasswordEncoder + BCrypt 비용 12를 사용한다. 8~72자이면서 UTF-8 72바이트 이하만 허용하고 원문은 변경하지 않는다. 새 라이브러리를 추가하지 않고 알고리즘 식별 접두사로 후속 변경 여지를 남긴다. Salt는 자동 생성한다. 비용의 운영 부하 평가는 배포 시 별도로 수행한다.
- 중복: 사전 조회 후에도 saveAndFlush에서 uk_users_email 위반을 확인해 409로 변환한다. 다른 무결성 오류를 중복 이메일로 오인하지 않는다. 트랜잭션 실패는 롤백한다.
- 보안: 가입 POST 전용 STATELESS 공개 체인만 CSRF 검사를 제외한다. 다른 경로는 기존 기본 인증·CSRF를 유지하며 JWT 단계에서 교체한다. 비밀번호·해시는 응답/요청 DTO toString에 노출하지 않는다. 가입에서 세션·토큰을 발급하지 않는다.
- 한계: 이메일 소유 검증, 로그인/Refresh/JWT, 초기 MANAGER 생성·승인·매장 범위 인가는 후속 단계다. 새 DDL이 필요하지 않아 기존 V1/V2를 변경하지 않는다. 기존 Compose DB·볼륨은 변경하지 않는다.
- 검증: 전체 79건 통과(기존 43 + 신규 36, 실패/스킵 0). 실제 동시 가입에서 201/409 및 단일 사용자 저장을 확인했다. 기존 DB 비의존 컨텍스트의 Repository 의존성 실패는 테스트 대역으로 해결했다. V1/V2 원문은 유지했다.


### D-20261110-01: 초기 MANAGER의 일회성 생성과 인가 서비스

- 상태: 채택.
- 선택: 공개 관리자 생성 API 대신 기본 비활성인 운영자 전용 비웹 ApplicationRunner를 사용한다. 운영자가 JASHOP_BOOTSTRAP_ENABLED와 이름/이메일/비밀번호 환경변수를 주입한다. 기존 SignupRequest 검증과 BCrypt 비용 12를 재사용하며 검증 실패에는 입력값을 담지 않는 고정 메시지만 사용한다.
- DB: 업무 도메인 17개와 별도로 V3 manager_bootstrap 운영 테이블을 추가했다. id=1 단일 행을 FOR UPDATE로 잠근 트랜잭션에서 사용자 생성 및 완료 기록을 함께 커밋한다. V1/V2는 변경하지 않는다. 단순 exists 검사만으로는 서로 다른 이메일의 동시 생성을 막을 수 없어 공통 잠금 지점을 추가했다.
- 정책: 생성 완료 기록이나 기존 MANAGER(비활성 포함)가 있으면 거부한다. 기존 이메일은 승격·덮어쓰기하지 않는다. 최초 계정은 ACTIVE/MANAGER/소속 없음이며 approvedBy/approvedAt은 null이다. 별도 완료 기록으로 생성 근거와 시각을 보존한다. 일반 승인 API에서는 이 생성 경로를 사용하지 않는다.
- 인가: UserAuthorizationService가 DB 사용자 상태와 역할/homeStoreId를 검증한다. requireActive, requireManager, requireStoreAssistantManager를 분리한다. 총괄에게 부매니저 전용 승인·배정 명령을 자동 허용하지 않는다. 타 매장/소속 없음은 거부한다.
- 한계: 로그인/JWT 및 기존 기본 인증과의 사용자 연결, 일반 승인/매장 API, 매장 활성·존재 및 현재 근무/업무 상태 검증은 후속 구현이다. 인증된 principal의 ID만 전달해야 한다. 현재 인가 조회는 외부 트랜잭션의 영속성 컨텍스트를 강제 갱신하거나 업무 명령과 권한 변경 사이의 잠금을 제공하지 않는다. 기존 Compose DB/볼륨 및 실제 계정은 변경하지 않았다.
- 검증: `./gradlew test --offline` 전체 99건 통과(기존 79 + 신규 20, 실패/오류/스킵 0). MySQL 동시 생성·롤백·DB 권한 변경 반영을 검증했다. 최초 AssertJ 인자 오류 및 테스트용 트리거 권한 오류는 수정 후 해결했다.
