**구현 범위(2026-11-10 코드 기준):** 공통 기반, Store/User 영속성, 회원가입, 초기 MANAGER 생성·인가 서비스 및 Store 조회/관리 API를 구현했다.

STORE-01은 페이지·활성 여부 필터·ID 오름차순 조회와 총괄 전용 생성/이름 변경/비활성화를 구현했다. 같은 매장 변경은 행 잠금으로 직렬화한다. 인증 principal 계약과 서비스 인가는 연결했으나 로그인/JWT가 없어 실제 계정 사용은 후속 단계다. STORE-02의 출퇴근·지원 등 매장별 업무 인가는 아직 미구현이다.
단계별 완료 및 검증 기록은 [개발 계획](07-development-plan.md)을 따른다.

## 1. 배경과 해결 대상

여러 상품 매장과 공용 창고를 운영하는 과정에서 직원의 현재 위치, 창고 확인 업무의 담당자, 마지막 확인 수량이 분산되어 있었다. POS 수량과 물리적 수량이 일치하지 않는 경우가 있었고, 실제 확인을 위해 창고로 이동하는 데 약 10분이 소요되는 일도 있었다. 지원 직원을 요청하거나 퇴근 시간을 공지하는 업무도 현장 상황에 따라 수시로 바뀌었다.

**목표:** 현장 직원이 모바일에서 상품을 검색하고 창고 확인 업무를 요청·수락·완료하며, 부매니저가 근무·인력 지원을 관리할 수 있는 공유 운영 플랫폼을 만든다.

**비목표:** POS 재고를 실시간 동기화하는 시스템, 자동으로 재고를 차감하는 시스템, 급여 산정 시스템이 아니다.

## 2. 사용자·역할·상태

| 구분 | 설명 | 기본 제한 |
|---|---|---|
| STAFF | 일반 직원 | 본인 근무와 현재 근무 매장 관련 업무 |
| ASSISTANT_MANAGER | 매장 부매니저 | 직원 기능 + 자신이 관리하는 기본 소속 매장 업무 |
| MANAGER | 전체 매장 총괄 매니저 | 직원 승인·전체 일정·공통 상품/위치 관리 |
| PENDING | 가입 후 승인 대기 | 업무 API·푸시 구독 불가 |
| ACTIVE | 승인되어 근무 가능 | 역할·매장·실제 근무 상태에 따라 권한 부여 |
| REJECTED | 가입 거절 | 업무 API 불가 |
| INACTIVE | 비활성 계정 | 재인증·재발급·업무 API 불가 |

- [확정] 회원가입자는 `name`, `email`, `password`를 제출하고 계정은 PENDING으로 생성된다. 역할·기본 소속 매장은 **총괄 매니저가 승인 시 결정**한다.
- [확정] 한 직원은 기본 소속 매장이 하나다. 부매니저 한 명은 한 매장에 소속되며 한 매장에 여러 부매니저가 있을 수 있다.
- [확정] `MANAGER`는 예외적으로 기본 소속 매장이 없어도 된다. 신규 총괄 권한 부여는 별도 보안 절차를 둔다.
- [확정] 직원이 다른 매장에 지원을 가도 기본 소속/부매니저 권한은 변경되지 않는다. 현재 근무 장소는 Attendance와 StaffAssignment에서 계산한다.
- [권장] 승인 대기·거절·비활성 계정도 상태 조회/오류 메시지는 받을 수 있으나 업무 데이터 조회는 금지한다.

## 4. 확정 근무 정책: 세 가지 시간의 차이

### 경기일
- 매니저가 출근 시각을 공지한다.
- 운영 상황에 따라 퇴근 시각이 매일 달라서 사전 예정 종료 시각이 **없을 수 있다**.
- `WorkSchedule.startAt NOT NULL`, `WorkSchedule.endAt NULL`.

### 비경기일
- 실제 운영 경험상 근무 시간이 오전 9시~오후 7시로 정해졌다.
- `startAt=09:00`, `endAt=19:00`으로 저장할 수 있다. **모든 비경기일에 동일 시간을 하드코딩하지 않는다.**

### 출퇴근과 퇴근 안내
- `Attendance.checkInAt`, `Attendance.checkOutAt`: 직원이 버튼을 누른 **실제 서버 시각 원본**.
- `CheckOutNotice.plannedCheckOutAt`: 현장에서 안내한 퇴근 예정 시각. 안내가 여러 번 바뀔 수 있다.
- `Attendance.recordedCheckOutAt`: 부매니저가 승인 단계에서 **00분 또는 30분**으로 직접 지정한 운영 기록 시각. 서버가 실제 시각을 자동 내림/반올림/올림하지 않는다.
- 예시: `startAt=10:00`, 퇴근 안내 `18:00`, 직원 실제 체크아웃 `18:12`, 운영 기록 `18:00`. **서로 다른 데이터**로 보관.
- 운영 기록값을 실제 근로시간·급여 산정의 정확한 증거로 대체하지 않는다. 실제 시간 변경은 감사 기능 없이는 허용하지 않는다.
- [권장] 승인 전 실제·운영 시각이 다르면 차이를 표시하고 사유 기록을 받는 확장점을 마련한다.

## 5. 현재 근무 상태 계산

| Attendance | 가장 최근 활성 StaffAssignment | 상태 | 현재 매장 |
|---|---|---|---|
| 없음/체크아웃 | 관계없음(정상 데이터라면 활성 배정 없음) | OFF_DUTY | 없음 |
| 활성 | 없음, RETURNED, CANCELLED | WORKING | WorkSchedule.storeId |
| 활성 | ASSIGNED | MOVING | 없음 |
| 활성 | ARRIVED | WORKING | StaffAssignment.toStoreId |
| 활성 | RETURNING | RETURNING | 없음 |

**한 가지 계산 결과를 재사용**한다: 현장 인원 목록, 재고 요청 수락 권한, 신규 알림 수신자, 지원 인원 배정 검증. 도착·복귀는 앱의 자기 확인이며 GPS 증명으로 취급하지 않는다.

## 6. 사용자 시나리오

### UC-01 경기일 근무와 퇴근 안내
1. 매니저가 10:00 출근, 예정 종료 `null`인 일정을 생성한다.
2. 직원이 체크인한다. 서버가 실제 시각을 기록한다.
3. 부매니저가 18:00 퇴근 안내를 발송했다가 18:30으로 재공지한다. 두 안내가 남는다.
4. 직원이 18:34에 실제 체크아웃한다.
5. 담당 매장 부매니저가 18:30 운영 기록을 입력해 승인한다. 18:34 원본은 유지된다.

### UC-02 공용 창고 확인 요청
1. 치어샵 근무 직원이 `143` 창고의 유니폼 L 옵션을 조회한다.
2. 해당 옵션은 마지막 확인 시각과 수량 또는 미확인 상태를 표시한다.
3. 재확인이 필요해 `URGENT` 요청을 생성한다. 담당 매장은 **요청 당시 그 직원이 실제 근무하던 매장**이다.
4. 해당 매장에 현재 근무 중인 직원 두 명이 동시에 수락한다. DB는 단 한 명만 성공시킨다.
5. 담당자가 0개를 입력해 완료하면 `StockVerification` 1건과 `StockRecord.quantity=0`이 남는다.

### UC-03 매장 간 지원 이동
1. 콜라보샵 부매니저가 치어샵에 직원 2명 지원을 요청한다.
2. 치어샵 부매니저가 승인하고 현재 치어샵에서 근무하는 직원 2명을 배정한다.
3. 이동 중 두 직원은 어느 매장의 근무 인원에도 포함되지 않는다.
4. 도착 확인 후 콜라보샵에서 근무 중인 것으로 계산한다.
5. 콜라보샵 부매니저가 지원 종료를 알리고, 실제 치어샵 복귀 확인 후 원래 매장 인원으로 돌아온다.

### UC-04 푸시 장애
1. 재고 확인 완료와 알림/전송 작업을 DB 트랜잭션에 커밋한다.
2. Web Push 제공자 장애로 전송을 실패한다.
3. 확인 결과와 알림함 데이터는 그대로 남고, Delivery Worker가 재시도한다.
4. 직원이 PWA를 열면 알림함과 현재 업무 상태를 REST로 다시 조회한다.

| 보안 | HTTPS, 비밀번호 단방향 해시, JWT 서명/만료/상태 검증, 최소 권한, 매장 범위 인가 |
| 시간 | DB UTC, 외부 ISO 8601 offset, 근무일·30분 경계는 Asia/Seoul 시간대로 해석 |
| 가용성 | Redis 장애는 최근 조회에만 영향, 외부 푸시 장애는 이미 커밋된 업무에 영향 없음 |
| 추적 | 누가/언제 요청·수락·완료·승인·이동했는지 저장, 민감 정보 로그 제외 |
| 성능 | 기본 20건, 최대 100건 페이지네이션 [권장]; 실제 측정 후 인덱스 개선 |
| 테스트 | 실제 MySQL Testcontainers로 동시성·제약·롤백 검증; 푸시 E2E는 실기기 |
| 접근성 | 모바일 우선, 푸시 알림 비활성 상태에도 업무 수행 가능 |

## 8. 범위 제외 및 미결 사항

**MVP 제외:** POS API 연동/재고 자동 차감, 불량·유실, AI 음성 검색, 급여 계산, GPS 기반 근무 인증, 지원 인원 자동 추천, Kafka.

**추가 결정 필요:** 다중 근무 일정/야간 근무, 일정 정정 감사, 기록 시각 차이 사유의 필수 여부, 활성 재고 요청을 가진 직원의 이동·체크아웃, 일부 지원 인원만 배정된 요청의 종료, 재고 확인 요청 취소/담당자 해제, 푸시 미수락 알림 임계시간, 계정 전환 기기 구독 정책, 데이터 보존 기간. 세부 목록은 [06-decisions.md](06-decisions.md).

## 9. 인수 기준

1. 같은 직원이 같은 근무일의 활성 일정을 두 건 갖지 않는다.
2. 체크아웃은 서버 실제 시각으로 남고 운영 기록으로 대체되지 않는다.
3. 30분 단위 기록은 부매니저가 직접 입력한다.
4. 한 요청의 동시 수락은 정확히 한 명만 성공한다.
5. 지원 중 직원이 다른 지원 요청에 중복 활성 배정되지 않는다.
6. 공용 창고의 마지막 확인값은 하나이며 매장별로 복제되지 않는다.
7. 알림의 수신자는 실제 현재 근무 매장 기준으로 결정된다.
8. Redis와 Web Push를 사용할 수 없어도 핵심 MySQL 업무는 유지된다.
9. 인가 실패·동시성 충돌·트랜잭션 롤백을 자동화 테스트로 재현할 수 있다.
